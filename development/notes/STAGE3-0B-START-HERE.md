# CoderGirl Stage 3.0B — Visual World Objects and generated mock main

Built on **Stage 3.0A**. Only four IDE source files were changed:

- `gamedesigner.cpp`
- `gamedesigner.h`
- `gamecodegen.cpp`
- `gamecodegen.h`

No firmware, `idelibs/` game helper implementation, hardware rendering, tilemap collision, spline mathematics or existing game project `main.c` was changed.

## Try the Game Object Properties window

1. Rebuild your Qt6 CoderGirl IDE using these sources.
2. Open or create a V1 `.sbgm` Game Designer document.
3. In **Game Resources**, right-click a **sprite** entry (not its category).
4. Choose **Configure Game Object...**.
5. Select `Collectable`, `Moving platform / Lift`, `Conveyor`, or `Spring / Bouncer`.
6. Set the hitbox dimensions, behaviour-specific fields, and optionally choose one of the splines already drawn in the Game Designer.
7. Optionally enable **Animate sprite frames**, with a valid frame range for the PPB atlas.
8. Click OK. The entry gets `[collectable]`, `[lift]`, etc. and its collision rectangle appears when selected in the world canvas. The rectangle scales with the normal canvas zoom.
9. Save the design. The object settings are saved under optional `gameObject` JSON fields in `.sbgm` **version 1**; existing designs remain compatible. Spline attachments are stored by stable ID so renaming a path does not disconnect objects.

Every sprite **instance** has independent settings. A duplicate sprite can behave differently from the original. Sprite positions, object physics, and spline controls stay in WORLD coordinates. Do not use `offset_spline()` on an attached object spline: the object helper handles camera drawing itself.

## Generate code and beginner reference

Use the existing **Generate V1 Game Code** action. In addition to `gameassets/gameassets.c/.h`, CoderGirl now creates:

- `gamehelpers/gameworlditems.c` / `.h` — generated initialisation, independent animations/splines, updates, physics hooks, pickup checks and drawing for configured game objects.
- `gamehelpers/gameworlditems.txt` — autogenerated instructions for those objects.
- **`maingame.c.txt` in the project root** — a deliberately non-compiling, readable reference that reflects the current game design. Double-click it in the Project Tree. It will not be included in the C compiler source list. This file is **regenerated and overwritten** on each Generate V1 Game Code action. Put personal notes in a different file.

The mock uses a full main-style example when the design has an attached tilemap and an ordinary sprite named **`player`**. Otherwise it shows the correct API integration sequence and explicitly identifies what is project-specific rather than inventing player/setup variables. Existing audio assets, installed helper guide filenames and sprite references are listed.

When objects are configured and required `.c/.h/.txt` helpers are missing, CoderGirl offers to install **only the missing files**. Existing programmer-edited C/H and guides are never silently overwritten. Attached splines are exported to `gamehelpers/splinepaths.c/.h` as part of generation. Moving objects use independent spline and frame-animation states even when sharing the same spline control points.

**IMPORTANT:** `drawworld()` now excludes managed collectable/world-object sprites from its generated drawing loop, because they are drawn camera-relative by `gameworlditems_draw()`. This avoids original-position "ghost" sprites. Ordinary sprites still use `drawworld()` when you call it; you must integrate your game's own player/camera rendering deliberately. The mock shows the correct draw order for a tilemap-based game.

## Things that have not changed

- Your real `main.c` is **never modified**.
- Your hardware-tested Stage 2.9 `gamespline` and Stage 3.0A `gamecollectables` / `gameworldobjects` implementations have **not been altered**.
- Physical collision remains the Stage 3.0A top-surface model, **not** solid platform sides/undersides or bulletproof high-velocity physics.
- There are no new toolbar rows, rounded corners, firmware changes or new executable game-engine dependencies.
- Generated C files **are replaced** when you request code generation, so don't use them for custom handwritten logic. Store custom code in `main.c` or separate programmer-owned files.

## Validation and limits

A representative generated `gameworlditems.c` containing a spline-animated pickup and spline-animated lift was compiled with `gcc -std=c11 -Wall -Wextra -Werror -fsyntax-only` against the actual SIDBOX V1 API and installed versions of the existing helpers. The existing helper templates passed the same check in the project's renamed form.

**Qt6 headers/libraries are unavailable in this build environment.** No Qt6 compiler run or visual IDE test was possible here. Please compile the IDE on Fedora and test first in a backed-up V1 game project. No real SIDBOX hardware tests were carried out for this Stage 3.0B editor integration.
