# Stage 5.49 (23 October 2026): Animated PPB HUD Progress Bars

## Editor

- Shared HUD Designer starts maximised.
- An additional draggable bar list sits under collectable HUD items. Sources: player Health, Lives, Score, every configured shared-player custom stat (e.g. `Fear`), and collectable totals discovered across all worlds.
- Drag the stat into the HUD canvas. The editor immediately opens the progress bar properties; cancel removes the attempted drop. Alternatively use **+ Animated progress bar (PPB)** to add and position a bar.
- In its properties choose any available PPB, 8x8 or 16x16 frame grid, starting frame index, frame count (1–64), frame duration in rendered frames (1–300 at 50 FPS), loop on/off, width in pixels, values for 0% and 100%, and a separate designer preview percentage.
- The atlas picker highlights the start frame. Frames run across the chosen frame-sized grid, left to right and top to bottom. A 16x16 frame uses the *contiguous* 2x2 arrangement already in the original PPB. A noncontiguous/custom four-cell stamp is **not** supported by this bar type.
- Drag existing bars to reposition, double-click to edit, right-click to delete. Designer preview advances through frames at 50 FPS. It shows the configured preview percentage; the firmware uses live stat values instead.

## Generated runtime

- Saved in `gamehud.sbhud` as a new optional `progressBars` array. Existing format/version 1 and older HUDs remain valid.
- `gamehelpers/gamehud.c` is generated by HUD Save and `Update Game Project`; `main.c` retains its existing `game_show_hud(...)` entry point.
- The specified frames are sampled from the source PPB **at generation time**, into const C pixel arrays, exactly like existing HUD icons. There is no additional `.ppb` output or manual TFCard copying.
- The PPB's indexed pixels are copied unchanged; the selected foreground CLUT decides the displayed colours. No palette re-quantisation or remapping.
- Each rendered cell references the *same* current animation frame. `gfx_drawbob()` draws full cells, then a final `gfxbob_t.width` shortened to the exact trailing filled pixel count. No full-screen second buffer or clipping API is required.
- Animation advances by one draw tick each `game_show_hud_at()` call (normally once per 50 FPS rendered frame). Loop mode wraps; one-shot mode holds the final frame.
- `gameworlds_state()->health/lives/score`, `gameplayer_stat_get("Name")` and `gameworlds_hud_total(kind)` supply values. Values at or below the configured 0% bound draw nothing; at or above 100% draw full width; other values scale linearly by pixel using 64-bit intermediates.
- Up to 32 bars per HUD. Width and size must fit in the HUD canvas. Invalid PPB paths, frames and ranges are rejected on export with an error rather than generating broken C.

## Validation and limitations

- `development/tests/test_stage549_hud_progress.py` checks editor/storage/PPB rules and extracts the **actual generated C format** to compile and run it with native GCC, checking 8x8 and 16x16 partial-cell clipping and Health/custom-stat/collectable reads.
- The Stage 5.45, 5.47 and 5.48 regressions also pass (older exact splash-version assertions updated for this release).
- Full Qt6 IDE build and STM32H743 hardware rendering not verified in this environment (Qt6 development headers/toolchain unavailable). Must rebuild and test on Fedora/SIDBOX.
- Frames are whole 8x8 or contiguous 16x16 PPB blocks, not independently repositioned or flipped stamp cells.
- The bar value is taken from the *live shared state API*. If custom code keeps a separate health variable, update `gameworlds_state()->health` when it changes, or choose a shared custom stat that is already kept current.
- HUD animations follow actual HUD draw calls, not a separate timer. Calls more/less often than once per VBlank change their effective speed.
