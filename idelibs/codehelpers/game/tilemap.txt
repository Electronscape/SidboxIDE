CODERGIRL V1 — ADVANCED TILEMAP + PLATFORMER
============================================

The editor stores two separate maps: 16-bit graphics IDs and 8-bit collision
IDs. Atlas animations are shared by graphics ID; no per-tile timers are needed.

1. Draw the level in the Game Designer Tilemap Editor and choose Export
   Tilemap. This writes gamelevels/level1.c and gamelevels/level1.h.
   Atlas pixels are NOT embedded in the C level: the PPB is read from SD
   ONCE at startup into RAM in its original PPB row-major layout,
   UNLESS gameassets has already loaded the very SAME PPB (then the level
   borrows that buffer, with no extra allocation). gfx_drawbob() draws
   each visible tile using an atlas cell index.

2. Include these files at the top of main.c:

#include "gamehelpers/gametilemap.h"
#include "gamelevels/level1.h"

3. Keep player physics and two FRONT buffer pointers outside main():

static game_tile_player_t physics = {0};
static gfx_bitmap_t *front[2] = {0};
static uint8_t draw_index = 0;

4. Once, after video setup and gameassets_init():

/* The SAME atlas PPB selected in the tilemap editor must be on the SD card.
   Always copy the latest version, including newly drawn animation frames.
   The generated wrapper validates dimensions, pixel count AND a content
   checksum. It catches stale SD artwork even when its size is unchanged. If loading
   fails, STOP the game rather than using blank/uninitialised graphics.
   Call after initMalloc() and before the first tilemap draw. */
if (!game_level1_load_atlas()) {
    dbug("ERROR: tile atlas missing, wrong size or could not be loaded\r\n");
    return 1;
}

front[0] = gfx_getfbuffer1();
front[1] = gfx_getfbuffer2();
gameassets_show_background();
game_tile_player_start(&physics, &game_level1, &player);
game_tilemap_animation_reset();

5. Inside the game loop, after gfx_lcdwait(), use your actual camera_x and
   camera_y (clamped to the map boundaries):

game_tilemap_animation_tick(1);  // Once per VBlank, not once per buffer
game_tile_player_run(&physics, getjoyport(), 1);
gfx_usebuffer(front[draw_index]);
gfx_setcolour(0);
gfx_rectf(0, 0, 480, 320);  // Erase this foreground page to transparent
game_tilemap_blit_view_cleared(&game_level1, camera_x, camera_y, 480, 320);
game_tile_player_screen(&physics, camera_x, camera_y);
gfx_drawbob(&player);
gfx_dispfbuffer(front[draw_index], front[draw_index ^ 1u]);
gfx_displaynow();
draw_index ^= 1u;

Use the actual sprite variable from gameassets.h instead of 'player'.
The transparent foreground colour is palette index 0; this lets the separate
background show through. Use the working full-viewport blitter baseline
before trying further scrolling optimisations.

Because gfx_rectf() just erased the entire foreground buffer to palette
index 0, game_tilemap_blit_view_cleared() can skip over 2400 extra per-cell
clear blits for a 480x320 viewport with 8x8 tiles. This is a rendering-only
optimisation: identical graphics and flip flags are submitted to BOB.

When you have NOT erased the whole target buffer first, use the original
self-contained game_tilemap_blit_view() instead: it still clears each
visible cell itself. The BOB index is 0-based; map graphic ID is 1-based.
Large atlases are safe because each visible tile selects its atlas row
and 8-bit column separately.

The animation functions make animated atlas tiles advance automatically.
No per-tile sprite objects are necessary. Frame timing is in VBlanks.

For collision, the level's exported graphics and collision maps stay separate.
The helper supports floors, walls, slopes, one-way tiles, hazards and doors.
The game decides what to do with hazards and doors.

When leaving a level, call game_level1_unload_atlas(). It frees a dedicated
atlas allocation, OR releases its borrowed pointer without freeing sprite RAM.
IMPORTANT: call game_level1_unload_atlas() BEFORE gameassets_shutdown()!
Do not re-initialise gameassets while the tilemap is borrowing its pixels.
Never call unload every frame. If you change the PPB on SD, restart/reload
both assets and the level so their pixels update. Map/collision/animation
code remains compiled, as before.

STAGE 3.3 — ATLAS SHARING
--------------------------
When you generate gameassets.c/.h AND level1.c/.h with Stage 3.3:
- If the sprite and tile atlas refer to exactly the SAME SD path, they
  share a pixel pointer. No second allocation, no second SD read.
- Checksums and atlas dimensions must match; mismatches fail safely.
- If they use DIFFERENT PPBs, the level loads its own checked buffer.
- Without generated gameassets.h, a standalone level still loads from SD.
- Regenerate BOTH gameassets and the tilemap to enable sharing.
- Update gamehelpers/gametilemap.c/.h to the new helper template first.
- If your level is loaded before gameassets_init(), sharing cannot occur;
  load gameassets first, as in the example above.

IMPORTANT: After updating CoderGirl to use SD atlases, update existing
project gamehelpers/gametilemap.c AND gametilemap.h to the new template
(before building), because the generated level calls the new loader API.
Do not overwrite programmer-edited files without saving a backup first.

STAGE 3.16 — MOVING PLATFORM / WALL COLLISION
-------------------------------------------
Game Designer automatically connects generated World Objects to the level's
collision map. The carried player is checked against solid tiles and slope
interiors, pixel by pixel. You do not need to edit main.c or generated
`gameworlditems.c` to enable this feature.

Update Project... to refresh BOTH gametilemap.c/.h and gameworldobjects.c/.h,
then regenerate V1 Game Code so the collision callback is wired up.
Game Objects WITHOUT an attached tilemap retain their previous behaviour.

STAGE 3.18 — CONTROLLED SPRING ARC / HELD-JUMP REGRESSION FIX
--------------------------------------------------------------
Ordinary jumps remain variable-height: release FIRE/UP early for a short hop;
hold FIRE/UP for the longer normal-jump arc.

Springs are intentionally different. World Objects gives the player a fixed
upward impulse using the spring's configured Launch Strength. Tilemap physics
recognises that external impulse and applies SHORT-HOP (extra) gravity
throughout the ascent, REGARDLESS of whether FIRE/UP is held or released.

Why? Stage 3.17 mistakenly gave every spring the LONG held-jump arc. Even
released jumps became enormous. This version restores the shorter spring arc
for both controls, matching the previously released-button behaviour.

The launch strength still controls how HIGH the spring can send the player:
15 is substantially stronger than the ordinary jump strength of 7. Reduce
spring Launch Strength if you want a smaller bounce. The optional Combine
Jump + Spring checkbox still intentionally adds a new-press jump impulse.

Use Game Designer -> Update Project... to refresh BOTH gametilemap.c and
.h; the game is our generated-code test, so do not patch gamehelpers or
main.c by hand. Neither Game Objects nor the exporter needs changing.


GAMERGIRL SD .MAP LOADER (Stage 3.24)
-----------------------------------
In Game Designer, choose Export Tilemap (.c / .map)...
Use Embedded .c for the old self-contained executable, or SD .map for
external tile graphics, collisions and tile animations. SD mode writes
gamelevels/level1.map plus small level1.c/.h. Copy the .map onto the
SIDBOX SD card at gamelevels/level1.map before running.

In SD mode, AFTER initMalloc() and gameassets_init(), call:
    if (!game_level1_load_map("gamelevels/level1.map")) return 6;
    if (!game_level1_load_atlas()) return 5;
At shutdown: game_level1_unload_atlas(); game_level1_unload_map();
Then gameassets_shutdown(). The SD map does not contain sprite BOB
assets, placed objects, trigger links, or the atlas PPB artwork.
Map loader verifies file content and leaves the current map untouched
on errors. Multiple map files may share a tile size and atlas.
An embedded-C export keeps game_level1_load_map() as a harmless no-op.
Update Project refreshes gamehelpers/gametilemap.c/.h from the SDK.

STAGE 3.27 — HAZARD CONTACT PHASES (TILES + ZONES)
---------------------------------------------------
GAME_TILE_HAZARD (collision type 5) is non-blocking. The SAME registered
four-argument callback now distinguishes three phases for either hazard source:

  GAME_HAZARD_TILE_ENTERED = first contact with any hazardous tile
  GAME_HAZARD_TILE_INSIDE  = every following physics update while overlapping
  GAME_HAZARD_TILE_EXITED  = first update after leaving all hazardous tiles

  GAME_HAZARD_ZONE_ENTERED = first contact with any active Hazard Zone object
  GAME_HAZARD_ZONE_INSIDE  = each following gameworlditems_after() while inside
  GAME_HAZARD_ZONE_EXITED  = first gameworlditems_after() after leaving zones

Register once after game_tile_player_start():

    game_death_set_callback(on_player_death, NULL);

    static void on_player_death(uint8_t reason, int32_t x, int32_t y, void *user)
    {
        (void)x; (void)y; (void)user;
        if (reason == GAME_HAZARD_TILE_ENTERED ||
            reason == GAME_HAZARD_ZONE_ENTERED) {
            /* play start-of-damage effect; optional immediate single hit */
        } else if (reason == GAME_HAZARD_TILE_INSIDE ||
                   reason == GAME_HAZARD_ZONE_INSIDE) {
            /* gradual damage: use a frame counter or elapsed-time timer */
        } else if (reason == GAME_HAZARD_TILE_EXITED ||
                   reason == GAME_HAZARD_ZONE_EXITED) {
            /* end effects, cancel timers */
        }
    }

GAME_DEATH_TILE_HAZARD and GAME_DEATH_ZONE retain their existing numeric values
and are aliases of the corresponding ENTERED reasons. Old callbacks that only
handle these reasons continue to behave as one-hit-on-entry callbacks.

INSIDE fires ONCE per physics update for tile hazards, and once per call to
gameworlditems_after() for Hazard Zones. At 50 updates/sec, INSIDE can fire
50 times per second: throttle damage in YOUR game code. The event system
never stops player movement automatically. Adjacent hazardous tiles and
zones are treated as a single contact: no false exit/re-entry. Crossing an
entire tile hazard at high speed still reports ENTERED, followed by EXITED.

When your own game determines actual death, call game_death_mark_dead() from
inside the callback. To programmatically kill the player from outside a
hazard callback, call game_death_trigger(GAME_DEATH_SCRIPT, x, y). Both
explicit death operations pause player physics. To respawn, call:

    game_tile_player_reset(&player_physics, spawn_x, spawn_y);

Do not respawn/reset on ordinary damage. A tile Hazard Zone and a placed
Hazard Zone may BOTH generate events if they overlap; keep separate damage
timers if you are using both. Update Game Project to replace helpers and
generated gameworlditems.c. Existing main.c is not overwritten.


STAGE 3.30 — PER-CELL GRAPHICS FLIPPING (X/Y)
-------------------------------------------------
Tilemap graphic IDs remain 16-bit and collision bytes remain unchanged.
The exported tilemap now also has a per-cell flip byte (bit 0 = X,
bit 1 = Y). These are passed to gfx_drawbob() as BLIT_FLAG_FLIP_X / Y.
This only mirrors artwork: collision types are separate properties.

Embedded C maps export game_level1_flips[] alongside graphics/collisions;
SD .map files exported by this IDE use SBMP version 2. Version 2 payload:
  graphics uint16 LE [w*h], collision uint8 [w*h], flip uint8 [w*h],
  followed by animation entries (unchanged, 6 bytes each).
The 20-byte header and FNV-1a checksum logic remain unchanged; the new
payload includes the flip bytes in that checksum. The updated loader also
accepts legacy version-1 maps, treating their flip flags as zero.

UI workflow:
- Pick a graphic ID from the atlas on the left.
- Tick Cell Flip X and/or Cell Flip Y, then paint on the map.
- To change an existing graphic's flags WITHOUT replacing the ID,
  select Paint graphic: Don't change graphic; then paint the flags.
- Set flip mode to Don't change flip flags for collision-only painting.
- In the stamp editor, use the same cell flip checkboxes when painting
  each stamp cell. Saved stamps retain independent flags per cell.
- Mirror stamp X/Y affects PLACEMENT only: source cell order is reversed
  and every constituent flip bit is XORed with the mirror bit. The
  original saved stamp stays unchanged. Horizontal stamp mirror also
  swaps the two directional slope collision IDs (3 and 4).
- There is NO ceiling-slope type: vertical stamp mirroring changes tile
  artwork but retains collision types, so check slopes manually.
- Stamps still expand into ordinary map cells; no runtime stamps exist.

To get this feature into your existing game, regenerate the level files
AND Update Game Project to copy the updated gamehelpers/gametilemap.h and
.c into the game. Copy the newly exported level1.map to SD if using SD.
The game must use the regenerated helper to understand v2 .map files.

The flags are defined in the SIDBOX graphics API header; whether the
currently installed SIDBOX firmware renders both correctly must be checked
on the actual device (native tests validate only the flag values passed).


STAGE 3.35 - COLLISION-ONLY SLOPE STAMPS
----------------------------------------
GamerGirl -> Tilemap Editor -> select a graphic stamp on the right ->
Collision Stamps tab -> Add -> draw a ground surface over the faded art.
Paint that collision stamp on the main map. ONLY collisions are modified;
graphic IDs and per-cell X/Y flipping are never changed by collision stamps.

A custom-slope cell uses collision type 7 (GAME_TILE_CUSTOM_SLOPE).
The corresponding map->slopes[] entry has tile_size height bytes per cell.
Each column has a surface height 0..tile_size measured from the tile top:
0 = completely solid in this column, tile_size = empty in this column.
There is solid ground below the line and no collision above it.
The old 0..6 collision types and existing 45-degree ramps still work.

For SD maps, the export is v3 ONLY IF custom-slope cells are present.
Payload: graphics uint16LE [cells], collision uint8 [cells],
flips uint8 [cells], slopeHeights uint8 [cells * tile_size],
then any 6-byte animation records. Checksum covers the full payload.
No custom slopes? The usual v2 .map is exported instead.
The loader accepts v1, v2 and v3; invalid data never replaces the level.

Existing game projects are offered an explicit helper upgrade for custom
slopes, which saves timestamped backup copies before replacing helpers.
Rebuild the .app after updating. Copy the new .map onto SD as usual.
In embedded mode, game_level1_slopes[] is compiled into the app.

Vertical stamp mirroring/ceilings/loops are NOT supported. Mirror X is.
Use gently sloping surfaces for natural walking; abrupt cliffs block.
If you re-paint a normal graphical stamp AFTER placing collision slopes,
its existing collision cells can overwrite the custom-slope layer.
Paint graphics first, collision stamps afterwards.

STAGE 3.36 - LINKED POINT-SLOPE COLLISION STAMPS
------------------------------------------------
Collision stamps are now reusable point-defined shapes. The editor saves
at least two points, fixed at the left and right sides of the stamp;
intermediate points can be inserted, dragged, and deleted. The faded graphical
stamp is a VISUAL REFERENCE ONLY. Map graphics and flip flags are separate.

New collisions use GAME_TILE_POINT_SLOPE (8). Each placed stamp has a
whole-instance record (origin tile x/y, shape index, horizontal mirror flag).
The per-cell shape_refs[] is a two-byte index to an instance, 0 means none.
Actual geometry is stored ONCE per named shape as connected (x,y) points,
not as one copied height sample per pixel column. At runtime tilemap.c samples
only the relevant line segment when testing player collision.

The game tilemap SD v4 format uses the 20-byte SBMP header. Header byte 18
contains number of shared shape definitions (1..128). Header byte 19 is 1
if LEGACY v3 height array data is also included, else 0. Payload:
    graphics: cells * 2 bytes (LE u16)
    collision: cells bytes, supports types 0..8
    flips: cells bytes
    [legacy slope heights: cells * tile_size bytes IF hdr[19] == 1]
    shape_refs: cells * 2 bytes (LE u16 instance+1)
    instance count: LE u16
    shape definitions: 8 bytes each: width, height, point_offset LE u16,
        point_count, zero reserved, zero reserved LE u16
    shape points: each x,y LE u16, 4 bytes per point
    placements: each tile_x, tile_y LE u16, shape ID u8, mirror flags u8
    animation records: 6 bytes each, same as older maps
Checksum: FNV-1a over entire payload; no raw pointers in files.
All references, points, stamp bounds and collision ownership are validated
before the loader replaces any live map. Older v1, v2, v3 files still load.

For 60x40 cells, new slope references require 4,800 bytes plus the small
point/instance tables. The old dense profile required 19,200 bytes at 8px.
Only old hand-painted type-7 slopes still incur dense legacy data. Those
cells have no saved placement identity; repaint them with new collision
stamps to remove that storage cost completely. Old .sbgm height-painted
STAMP DEFINITIONS are migrated to editable point arrays on opening, but
old ALREADY-PAINTED cells remain in legacy type-7 form.

In embedded C mode, game_level1_shape_refs, game_level1_shape_defs,
game_level1_shape_points and game_level1_shape_instances replace the
per-pixel height array for NEW point-defined slopes. Game engine and
main.c calling sequence are unchanged. The player helper follows the
shared ground profile and solid underneath. Ceiling collision, full
circular bodies and vertical flipping are not supported here.


STAGE 3.38 — RENDER/COLLISION CPU FAST PATHS
--------------------------------------------
The advanced V1 player now samples a point-defined collision line using
its overlapping segment endpoints rather than every pixel column. This
keeps EXACTLY the same surface height and mirrored slope result, while
reducing repeated work during moving-platform carry and walking.

The project-aware maingame.c.txt generator calls
    game_tilemap_blit_view_cleared(...)
after it has filled the entire foreground buffer with palette index 0.
The original game_tilemap_blit_view(...) remains available and unchanged
in behaviour for manual code that doesn't clear the full buffer.

Update Game Project makes a backup and refreshes gamehelpers/gametilemap.c
and .h. Existing main.c is NEVER overwritten. If your existing main.c
clears the foreground with gfx_setcolour(0); gfx_rectf(...) every frame,
you may opt into the faster renderer by replacing ONE call with the
_cleared version. Never use it on partially cleared buffers.

This is not a proven fix for intermittent dropped frames: the actual
SIDBOX timings still need measuring, including LCD wait and audio/IRQ.


GAMERGIRL CUSTOM COLLISION ZONES (STAGE 3.43)
---------------------------------------------
Custom 1..8 can be named in the tilemap editor (stored in .sbgm).
When exporting a level, the IDE writes these game-specific #defines into
  gamelevels/level1.h  (included automatically by generated maingame.c.txt)
For example, naming Custom 2 "Water" gives GAME_ZONE_ID_WATER, whose
value is 2. The always-available GAME_ZONE_ID_CUSTOM_1..8 remain stable.
Spaces/punctuation turn into underscores; duplicate names are suffixed.
Re-export the tilemap after renaming any zone. Do not edit gametilemap.h
for these names: that is the shared physics engine and may be upgraded.
Paint collision IDs 9..16 for nonblocking sensors; 17..24 for solid zones.
Both versions trigger callback zone numbers 1..8, with GAME_ZONE_ENTERED,
GAME_ZONE_INSIDE and GAME_ZONE_EXITED. Nonblocking effects require overlap;
solid zones trigger on physical contact at the player's hitbox boundary.
These types take the existing collision byte; SD .map remains version 4.

    static void on_zone(uint8_t zone, uint8_t event, int32_t x, int32_t y, void *u) {
        game_tile_player_t *p = (game_tile_player_t *)u;
        (void)x; (void)y;
        if (zone == GAME_ZONE_ID_WATER && event == GAME_ZONE_ENTERED)
            game_tile_player_set_physics_water(p);  // optional example
        if (zone == GAME_ZONE_ID_WATER && event == GAME_ZONE_EXITED)
            game_tile_player_set_physics_normal(p);
    }
    game_tile_set_zone_callback(on_zone, &player_physics);

Physics presets are optional: _normal, _ice, _water, _slow, _space,
_floating, _jetpack. Set custom values using game_tile_player_set_gravity()
and game_tile_player_set_walk_speed(). ICE uses momentum/friction; JETPACK
uses held FIRE to thrust upward while airborne. Presets do not modify
player health or dispatch events, and zone contact does not auto-apply them.


STAGE 3.44 — APPLY FORCE / SPACE THRUSTERS (OPTIONAL)
----------------------------------------------------
The V1 tilemap helper now supports an additive external velocity impulse:

    apply_force(&physics, 1.5f, -0.75f);  // +right, -up

The X/Y arguments are *velocity changes in pixels per frame*, not world
positions. One call is an impulse (explosion/push), repeated calls are
acceleration (wind, underwater currents, engine thrusters). Inputs clamp to
32 pixels/frame per direction for safe collision stepping. External horizontal
momentum is stored separately from ordinary joystick walking. No heap memory
or floating point calculations are used by the collision solver;
apply_force() converts float input to fixed point at its API boundary.

IMPORTANT: apply_force() does NOT advance the player position by itself.
Continue calling EXACTLY ONE of these once per frame:

    game_tile_player_run(&physics, getjoyport(), 1); // normal controls + force
    game_tile_player_step(&physics, 1);              // no built-in input + force

Both have the same tile collision, ceilings, slopes, hazards and zone callbacks.
If using a gameworlditems-managed player, still call gameworlditems_before()
and gameworlditems_after() around your chosen physics step as normal.

OPTIONAL zero-G, four-way joystick thrust example (add a boolean in_space
that your custom-zone ENTERED/EXITED callback sets):

    // On zone ENTERED:
    game_tile_player_set_physics_space(&physics);
    game_tile_player_set_gravity(&physics, 0); // literally weightless
    // In the game loop, after gameworlditems_before() if any:
    if (in_space) {
        uint8_t joy = getjoyport();
        if (joy & BTN_LEFT)  apply_force(&physics, -0.18f,  0.0f);
        if (joy & BTN_RIGHT) apply_force(&physics,  0.18f,  0.0f);
        if (joy & BTN_UP)    apply_force(&physics,  0.0f, -0.18f);
        if (joy & BTN_DOWN)  apply_force(&physics,  0.0f,  0.18f);
        game_tile_player_step(&physics, 1);
    } else {
        game_tile_player_run(&physics, getjoyport(), 1);
    }
    // On zone EXITED: game_tile_player_set_physics_normal(&physics);

Change X drag (0..100% lost per frame):
    game_tile_player_set_force_drag(&physics, 0);  // coast forever (space)
    game_tile_player_set_force_drag(&physics, 12); // drift slows down
Normal defaults to 12%; ICE 2%; WATER 18%; SPACE 0%. Gravity affects Y speed
independently, and can be adjusted with game_tile_player_set_gravity().
Wall collisions stop horizontal force, and ceilings stop upward travel.
Respawning resets momentum. Existing worlds without apply_force() are unchanged.

Update Game Project makes its normal backup, then installs the new
`gamehelpers/gametilemap.c/.h` along with the project-aware generated
maingame.c.txt. Existing main.c is NEVER overwritten. The .map binary
format, firmware and other world-object helpers require NO changes.


STAGE 3.53 — LONG LEVELS / SONIC-SIZED MAPS
-------------------------------------------
The map width and height are uint16_t in the original SBMP header, so no
new .map file version is necessary. The Tilemap Editor accepts up to 4096
tiles on either axis, but at most 262144 cells in TOTAL. The maximum for
one dimension changes when you edit the other dimension; shrink Tiles Y
before increasing Tiles X for a long horizontal level.

Examples: 2048 x 128 (16,384 x 1024 world pixels at 8 x 8), and
4096 x 64 (32,768 x 512 pixels at 8 x 8). 4096 x 256 is TOO LARGE.

For big levels, prefer SD .map mode over massive embedded C arrays.
The SD loader caps the resident map allocation at 3 MiB; maps with legacy
per-pixel slope data might exceed that budget and must use fewer tiles or
compact point-defined slopes. The exporter rejects oversized SD maps.
The selected atlas is a SEPARATE PPB allocation, so its size and all other
assets still count against available SDRAM.

The runtime draws only tiles visible in the 480 x 320 camera viewport;
map width alone does not increase the per-frame tile count. The v4
shared-slope loader now uses one map-sized allocation, eliminating a
second large temporary copy during level startup.

Update the project's gametilemap.c/.h helper through Update Game Project
after updating the IDE, and regenerate level1.c/.h and level1.map.
Existing smaller maps remain compatible. No firmware change is needed.
