CODERGIRL V1 — ADVANCED TILEMAP + PLATFORMER
============================================

The editor stores two separate maps: 16-bit graphics IDs and 8-bit collision
IDs. Atlas animations are shared by graphics ID; no per-tile timers are needed.

1. Draw the level in the Game Designer Tilemap Editor and choose Export
   Tilemap. This writes gamelevels/level1.c and gamelevels/level1.h.
   Atlas pixels are NOT embedded in the C level: the PPB is read from SD
   ONCE at startup into RAM in its original PPB row-major layout,
   UNLESS gameassets has already loaded the very SAME PPB (then the level
   borrows that buffer, with no extra allocation). gfx_drawbob() draws
   each visible tile using an atlas cell index.

2. Include these files at the top of main.c:

#include "gamehelpers/gametilemap.h"
#include "gamelevels/level1.h"

3. Keep player physics and two FRONT buffer pointers outside main():

static game_tile_player_t physics = {0};
static gfx_bitmap_t *front[2] = {0};
static uint8_t draw_index = 0;

4. Once, after video setup and gameassets_init():

/* The SAME atlas PPB selected in the tilemap editor must be on the SD card.
   Always copy the latest version, including newly drawn animation frames.
   The generated wrapper validates dimensions, pixel count AND a content
   checksum. It catches stale SD artwork even when its size is unchanged. If loading
   fails, STOP the game rather than using blank/uninitialised graphics.
   Call after initMalloc() and before the first tilemap draw. */
if (!game_level1_load_atlas()) {
    dbug("ERROR: tile atlas missing, wrong size or could not be loaded\r\n");
    return 1;
}

front[0] = gfx_getfbuffer1();
front[1] = gfx_getfbuffer2();
gameassets_show_background();
game_tile_player_start(&physics, &game_level1, &player);
game_tilemap_animation_reset();

5. Inside the game loop, after gfx_lcdwait(), use your actual camera_x and
   camera_y (clamped to the map boundaries):

game_tilemap_animation_tick(1);  // Once per VBlank, not once per buffer
game_tile_player_run(&physics, getjoyport(), 1);
gfx_usebuffer(front[draw_index]);
gfx_setcolour(0);
gfx_rectf(0, 0, 480, 320);  // Erase this foreground page to transparent
game_tilemap_blit_view(&game_level1, camera_x, camera_y, 480, 320);
game_tile_player_screen(&physics, camera_x, camera_y);
gfx_drawbob(&player);
gfx_dispfbuffer(front[draw_index], front[draw_index ^ 1u]);
gfx_displaynow();
draw_index ^= 1u;

Use the actual sprite variable from gameassets.h instead of 'player'.
The transparent foreground colour is palette index 0; this lets the separate
background show through. Use the working full-viewport blitter baseline
before trying further scrolling optimisations.

The renderer clears each tile area before drawing its BOB, so transparent
pixels and empty graphic ID 0 reveal the background correctly. The BOB
index is 0-based; the map graphic ID is 1-based. Large atlases are safe
because each visible tile selects its atlas row and 8-bit column separately.

The animation functions make animated atlas tiles advance automatically.
No per-tile sprite objects are necessary. Frame timing is in VBlanks.

For collision, the level's exported graphics and collision maps stay separate.
The helper supports floors, walls, slopes, one-way tiles, hazards and doors.
The game decides what to do with hazards and doors.

When leaving a level, call game_level1_unload_atlas(). It frees a dedicated
atlas allocation, OR releases its borrowed pointer without freeing sprite RAM.
IMPORTANT: call game_level1_unload_atlas() BEFORE gameassets_shutdown()!
Do not re-initialise gameassets while the tilemap is borrowing its pixels.
Never call unload every frame. If you change the PPB on SD, restart/reload
both assets and the level so their pixels update. Map/collision/animation
code remains compiled, as before.

STAGE 3.3 — ATLAS SHARING
--------------------------
When you generate gameassets.c/.h AND level1.c/.h with Stage 3.3:
- If the sprite and tile atlas refer to exactly the SAME SD path, they
  share a pixel pointer. No second allocation, no second SD read.
- Checksums and atlas dimensions must match; mismatches fail safely.
- If they use DIFFERENT PPBs, the level loads its own checked buffer.
- Without generated gameassets.h, a standalone level still loads from SD.
- Regenerate BOTH gameassets and the tilemap to enable sharing.
- Update gamehelpers/gametilemap.c/.h to the new helper template first.
- If your level is loaded before gameassets_init(), sharing cannot occur;
  load gameassets first, as in the example above.

IMPORTANT: After updating CoderGirl to use SD atlases, update existing
project gamehelpers/gametilemap.c AND gametilemap.h to the new template
(before building), because the generated level calls the new loader API.
Do not overwrite programmer-edited files without saving a backup first.

STAGE 3.16 — MOVING PLATFORM / WALL COLLISION
-------------------------------------------
Game Designer automatically connects generated World Objects to the level's
collision map. The carried player is checked against solid tiles and slope
interiors, pixel by pixel. You do not need to edit main.c or generated
`gameworlditems.c` to enable this feature.

Update Project... to refresh BOTH gametilemap.c/.h and gameworldobjects.c/.h,
then regenerate V1 Game Code so the collision callback is wired up.
Game Objects WITHOUT an attached tilemap retain their previous behaviour.

STAGE 3.18 — CONTROLLED SPRING ARC / HELD-JUMP REGRESSION FIX
--------------------------------------------------------------
Ordinary jumps remain variable-height: release FIRE/UP early for a short hop;
hold FIRE/UP for the longer normal-jump arc.

Springs are intentionally different. World Objects gives the player a fixed
upward impulse using the spring's configured Launch Strength. Tilemap physics
recognises that external impulse and applies SHORT-HOP (extra) gravity
throughout the ascent, REGARDLESS of whether FIRE/UP is held or released.

Why? Stage 3.17 mistakenly gave every spring the LONG held-jump arc. Even
released jumps became enormous. This version restores the shorter spring arc
for both controls, matching the previously released-button behaviour.

The launch strength still controls how HIGH the spring can send the player:
15 is substantially stronger than the ordinary jump strength of 7. Reduce
spring Launch Strength if you want a smaller bounce. The optional Combine
Jump + Spring checkbox still intentionally adds a new-press jump impulse.

Use Game Designer -> Update Project... to refresh BOTH gametilemap.c and
.h; the game is our generated-code test, so do not patch gamehelpers or
main.c by hand. Neither Game Objects nor the exporter needs changing.


GAMERGIRL SD .MAP LOADER (Stage 3.24)
-----------------------------------
In Game Designer, choose Export Tilemap (.c / .map)...
Use Embedded .c for the old self-contained executable, or SD .map for
external tile graphics, collisions and tile animations. SD mode writes
gamelevels/level1.map plus small level1.c/.h. Copy the .map onto the
SIDBOX SD card at gamelevels/level1.map before running.

In SD mode, AFTER initMalloc() and gameassets_init(), call:
    if (!game_level1_load_map("gamelevels/level1.map")) return 6;
    if (!game_level1_load_atlas()) return 5;
At shutdown: game_level1_unload_atlas(); game_level1_unload_map();
Then gameassets_shutdown(). The SD map does not contain sprite BOB
assets, placed objects, trigger links, or the atlas PPB artwork.
Map loader verifies file content and leaves the current map untouched
on errors. Multiple map files may share a tile size and atlas.
An embedded-C export keeps game_level1_load_map() as a harmless no-op.
Update Project refreshes gamehelpers/gametilemap.c/.h from the SDK.

STAGE 3.27 — HAZARD CONTACT PHASES (TILES + ZONES)
---------------------------------------------------
GAME_TILE_HAZARD (collision type 5) is non-blocking. The SAME registered
four-argument callback now distinguishes three phases for either hazard source:

  GAME_HAZARD_TILE_ENTERED = first contact with any hazardous tile
  GAME_HAZARD_TILE_INSIDE  = every following physics update while overlapping
  GAME_HAZARD_TILE_EXITED  = first update after leaving all hazardous tiles

  GAME_HAZARD_ZONE_ENTERED = first contact with any active Hazard Zone object
  GAME_HAZARD_ZONE_INSIDE  = each following gameworlditems_after() while inside
  GAME_HAZARD_ZONE_EXITED  = first gameworlditems_after() after leaving zones

Register once after game_tile_player_start():

    game_death_set_callback(on_player_death, NULL);

    static void on_player_death(uint8_t reason, int32_t x, int32_t y, void *user)
    {
        (void)x; (void)y; (void)user;
        if (reason == GAME_HAZARD_TILE_ENTERED ||
            reason == GAME_HAZARD_ZONE_ENTERED) {
            /* play start-of-damage effect; optional immediate single hit */
        } else if (reason == GAME_HAZARD_TILE_INSIDE ||
                   reason == GAME_HAZARD_ZONE_INSIDE) {
            /* gradual damage: use a frame counter or elapsed-time timer */
        } else if (reason == GAME_HAZARD_TILE_EXITED ||
                   reason == GAME_HAZARD_ZONE_EXITED) {
            /* end effects, cancel timers */
        }
    }

GAME_DEATH_TILE_HAZARD and GAME_DEATH_ZONE retain their existing numeric values
and are aliases of the corresponding ENTERED reasons. Old callbacks that only
handle these reasons continue to behave as one-hit-on-entry callbacks.

INSIDE fires ONCE per physics update for tile hazards, and once per call to
gameworlditems_after() for Hazard Zones. At 50 updates/sec, INSIDE can fire
50 times per second: throttle damage in YOUR game code. The event system
never stops player movement automatically. Adjacent hazardous tiles and
zones are treated as a single contact: no false exit/re-entry. Crossing an
entire tile hazard at high speed still reports ENTERED, followed by EXITED.

When your own game determines actual death, call game_death_mark_dead() from
inside the callback. To programmatically kill the player from outside a
hazard callback, call game_death_trigger(GAME_DEATH_SCRIPT, x, y). Both
explicit death operations pause player physics. To respawn, call:

    game_tile_player_reset(&player_physics, spawn_x, spawn_y);

Do not respawn/reset on ordinary damage. A tile Hazard Zone and a placed
Hazard Zone may BOTH generate events if they overlap; keep separate damage
timers if you are using both. Update Game Project to replace helpers and
generated gameworlditems.c. Existing main.c is not overwritten.
